# CLAUDE.md — RentRoll

Permanent operating rules for every Claude Code session in this repo.
These are not suggestions — treat them like lint rules that block a merge.

## 1. Spec is source of truth

- Before implementing or reviewing any screen, component, or business
  rule, read the relevant file under `spec/` — do not implement from
  memory or from a previous session's summary. Start at `spec/index.md`.
- `spec/index.md` → navigation and open contradictions
  `spec/foundations.md` → design tokens, component library, identifier
  scheme (A1–A5)
  `spec/cross-cutting.md` → universal rules, messages, permissions (E1–E4)
  `spec/product.md` → personas, data model, lifecycle, scope
  `spec/decisions.md` → schema-blocking decisions (D1–D12)
  `spec/screens/{landlord,tenant,shared,print}/*` → per-screen spec
- Use stable IDs (`L-04`, `T-01`, `S-02`, `P-01`, `L04-BTN-REMIND`, `D1`...)
  in commit messages, PR descriptions, and code comments that reference
  spec behavior. This is how a bug or question gets traced back to a line
  in the spec.
- `spec/decisions.md` overrides a conflicting source requirement **only**
  where a decision (D1–D12) has actually been recorded. Do not extend a
  decision's reasoning to a case it doesn't cover — treat that case as
  unresolved instead.
- An `> OPEN:` marker or an entry in `spec/index.md` § Open contradictions
  that has **no** corresponding entry in `spec/decisions.md` is still
  unresolved. Never silently pick one interpretation and implement it —
  implement around the ambiguity, or stop and ask the user. This applies
  even under time pressure or when one reading looks obviously "more
  correct."

## 2. Two global product rules (non-negotiable)

1. **No message ever leaves the system unless the landlord explicitly
   presses Send.** Any assistant/automation output is a draft in an
   editable field. Nothing dispatches on its own — no auto-send, no
   send-on-timer, no send-on-save.
2. **No tenant-facing screen or API response may expose:** rent amounts
   (except an explicitly approved own-receipt exception), repair/maintenance
   costs, another unit, or another tenant.

If a task — or a natural extension of a task — appears to require
violating either rule, **stop and escalate to the user instead of
implementing it**, even if the ticket doesn't mention the conflict.

## 3. Design system (A1, `spec/foundations.md`)

- Use only the A1 design tokens (colour, type scale, spacing, radius,
  elevation) defined in `spec/foundations.md`.
- No raw hex values inside components.
- No arbitrary/stock Tailwind colour classes (e.g. `text-blue-500`,
  `bg-slate-100`) — map to the token equivalents instead.

## 4. Component ownership (A2, `spec/foundations.md`)

- Use the A2 shared component library for buttons, form fields, stat
  cards, status chips, tables, detail panels, timelines, toasts, and
  confirm dialogs — don't rebuild these per feature.
- Feature lanes must not casually modify `src/components/ui`. Changes
  there affect every screen; treat it as a shared-ownership boundary.
- If a screen needs a shared component that doesn't exist yet, build the
  minimum local version in the feature lane and mark it:
  ```
  // PROMOTE: <short reason this belongs in src/components/ui>
  ```
  so it can be found and promoted later — don't add it to `ui/` yourself
  without discussion.

## 5. Money and dates

- **Money:** `₹`, Indian digit grouping (e.g. `₹1,00,000`), no decimals.
- **Dates:** `DD MMM YYYY` everywhere in the product (e.g. `06 Sep 2026`).

## 6. Tenant security boundary

- Tenant routes (`/u/:token`, T-01–T-05) are public, token-based, and
  have no sign-in. Treat every tenant-facing code path as effectively
  world-readable.
- Keep tenant routes structurally isolated from landlord/server-only
  code — don't import landlord-only logic, queries, or components into
  the tenant lane, and don't let a tenant-side query accidentally join
  across other units/tenants/rent/cost data (see rule 2 and
  `spec/cross-cutting.md` § E4 permission boundary tests).
- Remember there are **two distinct tokens** (`spec/decisions.md` D1):
  `unit.door_token` (durable, unit-level, anonymous) and
  `tenancy.tenant_token` (per-stay, expires when the tenancy ends). Don't
  conflate them.

## 7. Testing

- Focus tests on behavioural and security-critical logic: permission
  boundaries, token resolution, the two global rules, money/date
  formatting, rent lifecycle math — not on styling or rendering output.
- Run `npm run verify` before pushing (typecheck, lint, boundary check,
  tests, build — all must pass).
